# AGENTS.md

Контекст и правила для ИИ-агентов (и людей), которые работают с этим репозиторием. Здесь собрано то, что не видно из кода с первого взгляда: принятые решения, договорённости о процессе и грабли, на которые уже наступали. Как пользоваться ботом и как его развернуть - в [README.md](README.md).

Репозиторий публичный. Ничего конфиденциального - значений секретов, адресов серверов, идентификаторов чатов, имён аккаунтов - сюда, в README, код, тесты, коммиты и описания PR не пишется.

## Что это за проект

Telegram-бот: получает ссылку на публикацию Instagram и присылает её содержимое - рилс, фото или карусель из фото и видео. Работает в личке, в группах (по упоминанию `@бота`) и в inline-режиме. Карусель уходит одним сообщением-слайдшоу (rich message).

Бот намеренно открыт для всех пользователей Telegram. Allowlist, белые списки и ограничение доступа не предлагать: это решение владельца.

Стек: Python 3.13, `python-telegram-bot` 22.x, `yt-dlp`, `ffmpeg`, SQLite из стандартной библиотеки. Разворачивается Docker-образом через GitHub Actions на один сервер.

## Язык

- Общение с владельцем, описания PR, README, тексты, которые видит пользователь бота, - по-русски.
- Код, комментарии, docstring'и, сообщения коммитов, логи - по-английски.

## Устройство кода

`bot.py` - только точка входа. Всё остальное - пакет `nonnus/`, зависимости между модулями идут в одну сторону, сверху вниз:

| Модуль | Что в нём |
|---|---|
| `config` | настройки из окружения и `.env` |
| `links` | распознавание ссылок, каноничная форма, deep-link payload |
| `media` | `MediaItem`, сжатие видео и конвертация фото через ffmpeg |
| `instagram` | yt-dlp: разбор и скачивание поста, cookies и откат без них, подпись |
| `cache` | кэш `file_id` в SQLite |
| `delivery` | загрузка в storage-чат, отправка: слайдшоу, альбомы, одиночные файлы |
| `progress` | стадии подготовки поста для сообщения статуса; зависимостей в пакете нет |
| `status_message` | сообщение статуса: отдельное под ссылкой и подпись inline-заглушки |
| `preparation` | подготовка поста вне event loop, слоты, одна загрузка на ссылку |
| `inline` | inline-режим: результаты, заглушка, подмена на готовое медиа |
| `handlers` | `/start`, `/chatid`, ссылки в личку и в группах |
| `canary` | ежедневная проверка загрузки контрольного поста |
| `app` | сборка приложения, запуск и остановка фоновых задач |

`instagram` и `media` ничего не знают о Telegram. Циклических импортов нет и быть не должно.

**Модули импортируют друг друга целиком** и обращаются через модуль: `instagram.download_post(...)`, а не `from nonnus.instagram import download_post`. Так у каждого имени одно место, где его ищут, и `monkeypatch.setattr(instagram, "download_post", ...)` в тесте доходит до всех вызывающих. Импорт имени создал бы копию ссылки, до которой подмена не дотянется. Внутри модуля свои имена используются напрямую.

## Стиль кода

- Пишите так, как написан окружающий код: те же имена, та же плотность комментариев.
- Комментарии и docstring'и объясняют **почему**, а не пересказывают код. Особенно - неочевидные решения и то, что было проверено экспериментом.
- Аннотации в стиле `Optional[...]`, импорты сортируются по имени модуля независимо от формы `import x` / `from x import y`. Правила isort и pyupgrade в `ruff.toml` выключены намеренно - не включать.
- `ruff check .` должен быть чистым. Проверяются ошибки, а не оформление (`E4`, `E7`, `E9`, `F`, `B`). Длина строки 120 - ориентир, линтер её не проверяет.

## Процесс работы

- **Каждое изменение - отдельная ветка и pull request.** В `main` напрямую не коммитить: ветка защищена, изменения приходят только через PR. Префиксы веток: `feature/`, `fix/`, `refactor/`, `docs/`, `ci/`.
- **Мержит владелец.** Агент не мержит PR сам, если об этом не попросили явно.
- **Смерженные ветки удаляются автоматически**, хранить их не нужно.
- **Обязательные проверки PR:** `Lint and test` и `Build image`.
- **Коммиты:** заголовок по-английски в повелительном наклонении, в теле - что было не так и почему сделано именно так.
- **Описание PR:** по-русски, разделы «Зачем», «Что изменилось», «Проверка»; если есть последствия для уже работающего бота (кэш, сервер) - отдельный раздел.
- **Одна тема - один PR.** Если по ходу нашлась соседняя проблема из той же области - можно включить, явно назвав это в описании. Посторонняя - отдельным PR.

## Проверка изменений

- Перед PR: `pytest -q` и `ruff check .` проходят локально.
- Тесты не ходят в сеть и в Telegram: то, что туда ходит, подменяется заглушками, а проверяется логика вокруг. `tests/conftest.py` даёт каждому тесту свою SQLite-базу во временном каталоге.
- **Исправление ошибки сопровождается мутационной проверкой:** временно вернуть старое поведение (или сломать новое) и убедиться, что тесты падают. Тест, который проходит и с ошибкой, ничего не проверяет. Выжившая мутация - повод дописать тест, а не пропустить.
- Если существующий тест закреплял ошибочное поведение, его ожидание исправляется явно, с комментарием, что было не так.
- Утверждения о поведении внешних систем (urllib, ffmpeg, Telegram, GitHub) по возможности проверяются экспериментом, а не выводятся из памяти. Несколько ошибок в этом проекте нашлись именно так.
- Тесты, запускающие настоящий ffmpeg, на машине без него пропускаются, а в CI (где `CI=true`) - падают: CI ставит ffmpeg сам, и его отсутствие там - поломка, а не повод молча пропустить тесты.

## CI и деплой

- `.github/workflows/ci.yml` - на каждом PR: синхронность локфайла, проверка входов actions (`tools/check_action_inputs.py`), ruff, pytest с ffmpeg, сборка образа (в ней выполняется `import bot, nonnus.app` - сломанный импорт или путь к `assets/` роняет сборку, а не бота на сервере).
- `.github/workflows/deploy.yml` - на push в `main`: CI, сборка и публикация образа в GHCR, затем деплой по SSH.
- **Деплой ждёт ручного подтверждения в окружении `production`.** Подтверждает только владелец - агент деплои не подтверждает никогда.
- Ждёт подтверждения только самый свежий деплой: новый push отменяет ожидающий (`concurrency` с `cancel-in-progress`). Несколько PR можно смержить подряд и подтвердить один деплой. GitHub не умеет отменять только ожидающие, поэтому новый push отменит и уже идущий деплой - не мержить, пока подтверждённый деплой выполняется.
- Секреты лежат в окружении `production`, секретов уровня репозитория нет. Имена: `BOT_TOKEN`, `STORAGE_CHAT_ID`, `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `SSH_PORT`, `INSTAGRAM_COOKIES_B64`. Необязательные настройки - repository variables (список в README).
- GHCR: образ скачивается с токеном самого запуска (`GITHUB_TOKEN`), учётные данные на сервере живут во временном `DOCKER_CONFIG`. Отдельных секретов для реестра нет и не нужно.
- Скрипт деплоя работает под `set -e`: `appleboy/ssh-action` не останавливается на ошибке сам (входа `script_stop` у него больше нет, а неизвестный вход молча игнорируется).
- Actions прибиты по SHA коммита с комментарием-версией, базовый образ - по digest, раннер - `ubuntu-24.04`, а не `ubuntu-latest`. Двигать осознанно. Dependabot следит за actions, pip и Docker; обновления actions и pip приходят сгруппированными PR. pip проверяется ежедневно, а yt-dlp приходит отдельным PR: когда Instagram его ломает, исправление выходит за день-два, и его стоит мержить сразу.

## Зависимости

- `requirements.in` - намерение, правится руками. `requirements.txt` - локфайл, генерируется `pip-compile requirements.in`. Коммитятся оба; CI проверяет, что они не разошлись.
- `pip-compile --upgrade` - только когда версии нужно поднять намеренно.
- `requirements-dev.txt` не блокируется: локфайл, собранный на Windows, расходился бы с Linux.
- `python-telegram-bot` 22.x знает Bot API только до 10.0. Rich messages (Bot API 10.1+) сделаны вручную: `sendRichMessage` идёт через `Bot.do_api_request`, `InputRichMessageContent` описан в `nonnus/inline.py`. Когда библиотека получит поддержку - заменить на библиотечное.

## Безопасность и работа с данными

- Никогда не выводить и не логировать значения секретов, токенов и cookies - ни в терминал, ни в файлы, ни в PR.
- Токен бота едет в URL каждого запроса к Bot API (`/bot<токен>/метод`), поэтому всё, что логирует URL, логирует и токен. `app.configure_logging` держит `httpx`/`httpcore` на WARNING (иначе строка с токеном на каждый `getUpdates`) и ставит `RedactingFormatter`, который вычищает токены из готовой строки лога - сообщения, аргументов и traceback. Не понижать уровень `httpx` и не логировать запросы к Telegram в обход этого форматтера.
- Никогда не просить и не принимать пароль от аккаунта Instagram. Cookies выгружает владелец и сам кладёт в секрет.
- Боевую сессию Instagram локально не использовать: локальные тесты и проверки - без cookies.
- Не отправлять сообщения через бота - в storage-чат или кому-либо - без явного разрешения владельца на конкретную отправку.
- Cookies на сервере лежат с правами `600`. Если секрет `INSTAGRAM_COOKIES_B64` удалён, деплой удаляет и старый файл.

## Поведение бота: решения, которые нельзя ломать

**Пост уходит целиком или не уходит вовсе.** Отправленный пост кэшируется и дальше раздаётся из кэша всем, поэтому потерянный файл терялся бы навсегда. Не скачался слайд - `IncompletePostError`, ничего не отправляется и не кэшируется. Размер скачанного фото сверяется с `Content-Length`: Python не считает ошибкой ответ, оборвавшийся раньше заявленной длины.

**Альбомы.** Telegram принимает альбом из 2-10 файлов, а документ - только в альбоме с документами. Альбомы нарезаются поровну (11 - это 6 + 5, а не 10 + 1), файл, который Telegram взял лишь документом, уходит отдельным сообщением. Всё через `delivery.album_groups`.

**Кэш `file_id`.** SQLite (`INLINE_CACHE_DB`), ключ - нормализованная ссылка, режим WAL + autocommit, базу можно править руками на работающем боте. Если меняется формат записи или подпись - поднять `INLINE_CACHE_VERSION` в `nonnus/cache.py`, иначе старые записи так и будут раздаваться. `file_id` принадлежит боту, который загрузил файл: на отказ Telegram по `file_id` запись удаляется и пост готовится заново; на любую другую ошибку отправки кэш не трогается и повторной отправки нет (после таймаута сообщение могло уже дойти).

**Статус и ошибки.** Сообщение статуса под ссылкой всегда завершается - удаляется или становится текстом ошибки, в том числе при непредвиденном исключении (`deliver_post` ловит всё). Прогресс идёт через `nonnus/progress.py`: поток скачивания сообщает стадию через `ContextVar`, который `asyncio.to_thread` переносит в поток, так что сигнатуры не меняются и `instagram` не знает о Telegram. Выбранная inline-заглушка показывает тот же прогресс в своей подписи (`status_message.PlaceholderStatus`). Перед подменой на пост статус завершается (`settle`), иначе запоздалая правка заменила бы подпись поста; каждая правка подписи передаёт кнопку заглушки заново - правка без `reply_markup` снимает клавиатуру. Глобальный обработчик ошибок в `app.py` отвечает пользователю только в личке: в группе упавшее сообщение могло быть адресовано не боту.

**Параллельность.** Апдейты обрабатываются параллельно (`concurrent_updates`). Всё блокирующее - yt-dlp, ffmpeg, ffprobe - выполняется вне event loop (`asyncio.to_thread`), тяжёлое - под `DOWNLOAD_SLOTS` (`MAX_PARALLEL_DOWNLOADS`). Одна ссылка, запрошенная несколькими людьми сразу, скачивается один раз. Неудачная подготовка запоминается на минуту для inline-запросов, которые клиент шлёт на каждое нажатие клавиши; ссылка в личку всегда пробует заново.

**Cookies Instagram.** Мёртвая сессия хуже, чем никакой: с ней yt-dlp идёт по пути со входом и падает там, где путь без входа отдал бы публичный пост. Поэтому запрос к API - с откатом без cookies. Сессия распознаётся косвенно («с cookies не вышло, без них вышло»), по формулировкам ошибок yt-dlp ничего не определять. Cookies откладываются на час и владельцу уходит уведомление только после двух отказов подряд; успешный запрос с cookies обнуляет счёт.

**Один запрос к API Instagram на пост.** Разбор (`probe_post`) делается без обработки (`process=False`), и видео скачиваются из этого же результата (`process_ie_result` на копии), прямо с CDN. Второй запрос к API, как было раньше, давал Instagram ещё один шанс ответить с сервера «empty media response» - разбор проходил, а скачивание через секунду падало. Обработанный результат для этого не годится: yt-dlp сохраняет выбранный при разборе формат по умолчанию и не применяет наш. Проход за видео идёт с cookies или без - так, как прошёл разбор, - и своего отката не имеет: API он не трогает.

**Логи неудач.** Неудачная подготовка поста логируется полностью один раз - глобальным обработчиком ошибок как сбой фоновой задачи, с пометкой `While preparing <ссылка>` в traceback. Все, кто её ждал (личка, inline, выбор заглушки), пишут одну строку через `preparation.describe_failure` - иначе inline-запрос на каждое нажатие клавиши добавлял бы по traceback. Одна и та же сессия может работать с сервера и не работать с другого IP - это не значит, что файлы cookies разные.

**Фото.** yt-dlp не строит `formats` для фото Instagram - их адреса есть только среди `thumbnails`, поэтому разбор идёт с `ignore_no_formats_error`, а фото скачиваются напрямую. Среди вариантов есть квадратные кропы для сетки профиля (маркер `c<x>.<y>.<w>.<h>a` в `stp`); без входа у вариантов нет размеров. Выбирается полный кадр наибольшего размера, кроп - никогда.

**Сжатие видео.** Размер файла задаёт битрейт × длительность, разрешение - только качество. Ступени `VIDEO_COMPRESSION_HEIGHTS` ограничивают длинную сторону и никогда не увеличивают кадр; каждая следующая попытка снижает битрейт на величину промаха, не ниже `VIDEO_COMPRESSION_MIN_VIDEO_KBPS`; видео, которое не влезет в лимит Telegram даже на нижней границе, не кодируется вовсе. Видео в другом кодеке (например, VP9) перекодируется в H.264, а всё перекодированное - в `yuv420p`: иначе Telegram на iOS показывает застывший кадр со звуком.

**Ссылки.** Поддерживаются `/p/`, `/reel/`, `/reels/`, `/tv/`, домены `instagr.am` и `m.instagram.com` и ссылки из профиля вида `/<username>/p/<code>/`. Тип и код читаются с конца пути, имя пользователя отбрасывается - это один пост и одна запись в кэше. Ссылки из меню «Поделиться» - `/share/<id>`, `/share/reel/<id>`, `/share/p/<id>` - кода поста не содержат: прежде всего остального `preparation.resolve_link` узнаёт, на какой пост они ведут (запомненный результат, иначе запрос `HEAD` без перехода по редиректам). Instagram отвечает редиректом на пост только мобильному браузеру или краулеру; десктопному - JS-оболочкой, одинаковой и для настоящей ссылки, и для выдуманной. Проверено вживую.

**Подписи.** «Пост @автор» или «Рилс @автор» со ссылкой на публикацию; рилс - это одиночное видео, что бы ни было в ссылке.

**Inline.** Первый запрос по новой ссылке получает заглушку, которая после выбора сама подменяется на готовое медиа - для этого у бота должна быть включена inline feedback (`/setinlinefeedback` в BotFather). У `InlineQueryResultCachedPhoto` клиенты Telegram не показывают заголовок - текст заглушки нарисован на самой картинке. Заглушек две, по тому, что известно из ссылки до обращения к Instagram: `/reel/`, `/reels/`, `/tv/` - «Готовлю рилс...», всё остальное - «Готовлю пост...» (`/p/` бывает и фото, и каруселью, и видео). Карусель предлагается и целиком (слайдшоу), и по файлам с кнопкой «Посмотреть карусель» - deep link в личку.

**Фоновые задачи.** `Application.stop()` ждёт все задачи, созданные через `application.create_task`, поэтому бесконечный цикл (как проверка в `canary`) запускается обычным `asyncio.create_task` в `post_init` и отменяется в `post_stop` - иначе каждый деплой висел бы на остановке контейнера. Дождаться отменённой задачи - `asyncio.gather(task, return_exceptions=True)`, а не `contextlib.suppress(CancelledError)`: тот проглатывает и отмену того, кто ждёт.

## Сервер

- Бот работает в Docker Compose под UID/GID пользователя, от имени которого идёт деплой; данные - в каталоге `data/` рядом с `docker-compose.yml`.
- Файлы `inline_cache.sqlite3`, `-wal` и `-shm` - одна база: `-wal`/`-shm` не удалять, для резервной копии - `sqlite3 ... ".backup ..."`, а не копирование одного файла. Править базу `sqlite3` от того же пользователя, что и контейнер.
- Команды для осмотра и правки кэша - в README.

## Локальная среда владельца

Разработка идёт на Windows:

- Python проекта - `.venv\Scripts\python.exe`; просто `python` в Git Bash может оказаться заглушкой Microsoft Store.
- В рабочей копии переводы строк CRLF (`core.autocrlf=true`), в репозитории - LF. Скрипты, которые правят файлы по многострочным шаблонам, должны это учитывать.
- Heredoc'и в Git Bash могут портить обратные слэши и кавычки - код с такими символами лучше писать в файл напрямую, а не через heredoc.
