# План развития

Что можно сделать с ботом дальше, в каком порядке и почему. Это кандидаты, а не обязательства: каждый пункт делается отдельным PR, когда владелец решит его взять. Сделанное отсюда убирается, а принятые по ходу решения переезжают в [AGENTS.md](AGENTS.md).

## Проверить вживую

Всё из #47-#50 работает на сервере с 25 сентября. Ниже то, что тесты проверить не могут: Telegram и GitHub в них подменены заглушками.

- [ ] Inline по новой ссылке `/reel/...` показывает картинку «Готовлю рилс...», по новой `/p/...` - «Готовлю пост...».
- [ ] В подписи выбранной заглушки идёт прогресс, а кнопка «Открыть в Instagram» при этом не пропадает. Бот передаёт её при каждой правке, потому что правка без `reply_markup` снимает клавиатуру, - это известно из документации, а не проверено.
- [ ] Статус называет вид поста. Карусели проверены вживую, а «Скачиваю рилс...» и «Скачиваю фото...» - нет: не нашлось публичного одиночного поста, который открывается без входа.
- [ ] При первом двойном мерже деплой, который ждёт подтверждения, отменяется сразу, а подтверждения ждёт только последний. Эксперимент проверял задачу, которая ждала раннер, а не подтверждение.

## Очередь

Порядок такой: сначала защита аккаунта Instagram, от которого скачивают все пользователи, потом способ проверять изменения до рабочего бота, потом новые возможности.

### 1. Лимит на новые скачивания для одного пользователя

**Зачем.** Бот открыт для всех, а скачивает от одного аккаунта Instagram. Если один человек зальёт сотню ссылок, Instagram может закрыть сессию, и это заденет всех. Сервер при этом занят чужой очередью.

**Что сделать.**
- Считать только новые подготовки. Посты из кэша - без ограничений.
- В inline считать подготовки, а не запросы: клиент шлёт запрос на каждое нажатие клавиши.
- Сверх лимита - понятный ответ, когда можно снова.
- Счётчики можно держать в памяти: сброс при деплое не страшен.

**Решить.** Сколько новых постов и за какое время. Одинаковый ли лимит для лички, групп и inline.

Это ограничение частоты, а не доступа: бот остаётся открытым для всех.

### 2. `/stats` для владельца

**Зачем.** Видеть проблему раньше, чем о ней напишут: сколько запросов, сколько ушло из кэша, какие были ошибки. И видно, срабатывает ли лимит из пункта 1.

**Что сделать.** Счётчики за сутки в той же SQLite. Команда отвечает только в storage-чате.

**Решить.** Хранить ли что-то о пользователях. Для статистики хватает чисел.

Удобно делать вместе с пунктом 1: счётчики нужны обоим.

### 3. Тестовый бот и ветка `develop`

**Зачем.** Список «Проверить вживую» выше - это то, что сейчас проверяется только на рабочем боте: inline, слайдшоу, правка сообщений, поведение деплоя. С тестовым ботом это можно проверить до того, как увидят пользователи.

**Что сделать.**
- Второй бот в BotFather, свой storage-чат, своя папка `data` на том же сервере.
- Окружение `staging` со своими секретами.
- `develop` - ветка по умолчанию: PR и Dependabot идут в неё, мерж сразу выкатывает тестового бота.
- Релиз - один PR из `develop` в `main`, обычным merge, а не squash, иначе история веток разойдётся.

**Нужно от владельца.** Токен второго бота, storage-чат, секреты окружения `staging`.

**Решить.** Давать ли тестовому боту cookies. Одна сессия с двух ботов - двойная нагрузка на аккаунт, так что скорее без них.

Без тестового бота `develop` не нужен: несколько PR и так выкатываются одним подтверждённым деплоем.

### 4. Текст поста в подписи

**Зачем.** Сейчас подпись - «Пост @автор» со ссылкой, а текст поста часто не менее важен.

**Что сделать.** Добавлять начало оригинального текста. Подпись к медиа в Telegram - до 1024 символов, вместе с «Пост @автор» и пометками бота о сжатии и звуке.

**Решить.** Всегда или настройкой, и сколько символов.

**Цена.** Меняется формат подписи, поэтому по правилу из AGENTS.md поднимается `INLINE_CACHE_VERSION`, и каждый закэшированный пост при следующем запросе скачается заново. Это разовая нагрузка на Instagram.

### 5. Свой сервер Bot API

**Зачем.** Облачный Bot API принимает от бота файлы до 50 МБ, свой сервер `telegram-bot-api` - до 2000 МБ. Длинные видео уйдут без сжатия или с мягким, и ответ «файл слишком большой» почти исчезнет.

**Цена.**
- Ещё один контейнер на сервере и место на диске под файлы.
- `api_id` и `api_hash` с my.telegram.org: их получает владелец и кладёт в секреты.
- Переделка отправки файлов и пересмотр настроек сжатия.

**Проверить до начала.** Чтобы перейти на свой сервер, бот выходит из облачного (`logOut`) и вернуться туда сможет не раньше чем через 10 минут. Что при этом будет с `file_id` в кэше, проверить экспериментом. Если они перестанут работать, кэш пересоберётся сам: бот уже умеет готовить пост заново, когда Telegram отвергает `file_id`.

### 6. Сторис и хайлайты

**Зачем.** Частый запрос.

**Цена и риск.** Без входа их не скачать, так что всё держится на cookies и нагружает аккаунт бота. Если Instagram закроет сессию, бот продолжит скачивать публичные посты без входа, но то, что требует входа, перестанет работать.

**Проверить до начала.**
- Как yt-dlp сейчас справляется со сторис.
- Какого вида у них ссылки.
- Как их кэшировать: сторис живут сутки.

Не раньше пункта 1.

## Когда появится повод

- **Rich messages из библиотеки.** Слайдшоу отправляется вручную: `python-telegram-bot` 22.x знает Bot API только до 10.0. Когда выйдет версия с Bot API 10.1+ - её принесёт Dependabot, - заменить `sendRichMessage` через `do_api_request` и самописный `InputRichMessageContent` на библиотечные.
- **Instagram отвечает серверу пустотой.** С IP сервера Instagram иногда отвечает «empty media response» на посты, которые с другого адреса скачиваются. Пока это разовые сбои. Если станет постоянным - об этом сообщит ежедневная контрольная проверка, - тогда искать другой путь: другой IP для запросов к Instagram или рабочую сессию cookies.

## Решено не делать

- **Allowlist и ограничение доступа.** Бот намеренно открыт для всех.
- **Ветку `develop` без тестового бота** - см. пункт 3.
